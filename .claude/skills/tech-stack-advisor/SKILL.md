Skill นี้**ต่างจาก `architecture-doc-sync`/`data-api-doc-sync`/`detailed-design-doc-sync`** ตรงที่ 3 skill นั้นผลิตเอกสาร**แบบ conceptual ที่ห้ามผูกกับ stack** แต่ skill นี้มีหน้าที่ตรงข้าม — ช่วย**เลือก stack จริง** และเขียนเอกสารที่**ผูกกับ stack โดยเจตนา** (มีชื่อ framework/library/บริการ hosting จริงตรงๆ ในเนื้อหาหลักได้เต็มที่) เพราะนี่คือเอกสารสายเทคนิคระดับ "physical/implementation" ที่ `architecture.md` เคยกันพื้นที่ไว้ล่วงหน้าแล้วว่า "a separate, later stack-specific technical design doc may still join this folder"

หัวใจของ skill นี้คือ**การถามให้ครบก่อนแนะนำ** — ห้ามข้ามไปแนะนำ stack ทันทีโดยไม่ถามบริบทให้ครบตามขั้นตอนด้านล่าง แม้ user จะรีบก็ตาม (ถ้า user ยืนยันว่าอยากให้ข้ามคำถามบางหมวดจริงๆ ให้บันทึกไว้ในเอกสารว่าหมวดนั้น "ไม่ได้สอบถามตามคำขอของ user" แทนที่จะเดาคำตอบเอง)

## 1. ตรวจสอบก่อนว่า scope ของการตัดสินใจนี้คืออะไร (คำถามแรกที่ต้องถามเสมอ)

โปรเจกต์นี้ ("My Today Project") **มี stack ที่เลือกและ build ไปแล้ว** (React + TypeScript + Vite + Tailwind CSS, client-only, LocalStorage + IndexedDB, deploy บน Vercel — ดู `CLAUDE.md` ส่วน Project state/Architecture) ดังนั้นก่อนเริ่มสัมภาษณ์เชิงลึก ต้องถาม user ด้วย AskUserQuestion ก่อนเสมอว่าคำแนะนำ/เอกสารนี้มีไว้เพื่ออะไร พร้อมตัวเลือกอย่างน้อย 3 แนวทาง เช่น:

- **บันทึกย้อนหลัง + ยืนยันเหตุผลของ stack ที่ใช้อยู่แล้ว** (React/Vite/TS/Tailwind + client-only storage) เป็นเอกสารทางการ — ข้อดี: ตรงกับความจริงที่ build ไปแล้ว ไม่มีความเสี่ยงเปลี่ยน stack กลางทาง; ข้อเสีย: ไม่ได้ประเมินทางเลือกอื่นจริงจัง เพราะผลลัพธ์ถูกกำหนดไว้แล้ว
- **ประเมิน stack ใหม่สำหรับ scope ที่ยังไม่มีในระบบปัจจุบัน** (เช่น backend/service สำหรับ "Daily Orchestrator" AI ใน phase หลัง Freeze ที่ปัจจุบันยังไม่มี backend เลย) — ข้อดี: เป็นการตัดสินใจที่ยังเปิดกว้างจริง มีประโยชน์ต่ออนาคต; ข้อเสีย: เป็นการวางแผนล่วงหน้าไกลเกินสถานะปัจจุบันของโปรเจกต์ (Sprint 9-11 ยังไม่เริ่มด้วยซ้ำ)
- **ประเมิน stack แบบเริ่มใหม่ทั้งหมด สมมติไม่มีของเดิม** (thought experiment / ใช้เป็น reference สำหรับโปรเจกต์อื่น) — ข้อดี: ได้เอกสารเปรียบเทียบที่เป็นกลางที่สุด ใช้ซ้ำกับโปรเจกต์อื่นได้; ข้อเสีย: ไม่ actionable กับโปรเจกต์นี้เลยเพราะ Sprint 1-8 build เสร็จและ deploy ไปแล้วจริง เปลี่ยน stack ตอนนี้คือ rewrite ทั้งระบบ

ถ้า user ระบุ scope อื่นที่ชัดเจนอยู่แล้วในคำขอ ให้ใช้ตามนั้นแทนไม่ต้องถามซ้ำ

## 2. สัมภาษณ์เข้มข้นตามหมวด (ทำทีละหมวด อย่ารวบทุกอย่างในคำถามเดียว)

ถามผ่าน AskUserQuestion เป็นรอบๆ (รอบละไม่เกิน 4 คำถามตามข้อจำกัดของเครื่องมือ) ครบทุกหมวดต่อไปนี้ที่เกี่ยวข้องกับ scope ที่ยืนยันในขั้นตอนที่ 1 — ถ้าบางหมวดไม่เกี่ยวข้องกับ scope ที่เลือก (เช่น เลือก "บันทึกย้อนหลัง" ก็ไม่ต้องถามเรื่อง budget ใหม่เพราะไม่มีการใช้จ่ายเพิ่ม) ให้ข้ามหมวดนั้นได้ แต่ต้องระบุเหตุผลที่ข้ามไว้ในเอกสารด้วย:

1. **Functional scope** — ระบบ/โมดูลนี้ต้องทำอะไรบ้าง (ฟีเจอร์หลัก), มีข้อมูลอะไรบ้างที่ต้องเก็บ/ประมวลผล, ต้องเชื่อมกับระบบภายนอกไหม
2. **Non-functional requirements** — ขนาดผู้ใช้ที่คาดไว้ (concurrent users/data volume), ความต้องการด้าน performance/latency, ต้องรองรับ offline ไหม, ความพร้อมใช้งาน (uptime) ที่ต้องการ
3. **ทีมและการดูแลรักษาต่อ** — ขนาดทีม, ภาษา/framework ที่ทีมถนัดอยู่แล้ว, เปิดรับเรียนรู้เทคโนโลยีใหม่แค่ไหน, ใครจะดูแลต่อระยะยาว (solo dev/ทีม/ส่งต่อให้คนอื่น)
4. **งบประมาณและ timeline** — งบสำหรับ hosting/บริการภายนอก (ฟรีเท่านั้น/มีงบจำกัด/ไม่จำกัด), แรงกดดันด้านเวลา (ต้องรีบ ship เทียบกับลงทุนเรียนรู้ของใหม่ได้)
5. **Hosting/Deployment และ Data** — ต้องการ hosting แบบไหน (serverless/PaaS/self-hosted/cloud provider เจาะจง), รูปแบบข้อมูล (relational/document/key-value), ต้องการ ACID transaction ไหม
6. **Security/Compliance** — ข้อกำหนดด้านความปลอดภัย/กฎหมายที่ต้องปฏิบัติตาม (เช่น PDPA ที่โปรเจกต์นี้เคยพิจารณาไว้ระดับ Privacy Notice ใน Sprint 6), การเข้ารหัสข้อมูล, data residency
7. **ข้อจำกัด/การตัดสินใจที่ fix ไว้แล้ว** — มีอะไรที่เปลี่ยนไม่ได้อยู่แล้วบ้าง (เช่น "ต้อง client-only ต่อไป" ตาม Project purpose ของโปรเจกต์นี้ที่ระบุไว้ใน `CLAUDE.md`) ต้องเคารพข้อจำกัดเดิมเสมอ ไม่เสนอ stack ที่ขัดกับข้อจำกัดที่ fix ไว้แล้วโดยไม่ถามยืนยันก่อน

## 3. สังเคราะห์และเสนอ stack อย่างน้อย 3 ทางเลือก พร้อมข้อดี/ข้อเสีย

จากข้อมูลที่ได้ครบแล้ว วิเคราะห์และเสนอ**อย่างน้อย 3 stack ที่เป็นไปได้จริง** (ไม่ใช่ 3 ตัวเลือกที่ห่างไกลความจริงเพื่อให้ครบจำนวน) พร้อมข้อดี/ข้อเสียของแต่ละอันเทียบกับ requirement/constraint ที่เก็บมาในขั้นตอนที่ 2 แสดงเป็นตารางเปรียบเทียบให้ user เห็นชัดเจน แล้วให้คำแนะนำว่าอันไหนเหมาะที่สุดพร้อมเหตุผลอ้างอิงกลับไปยังคำตอบที่ user ให้ไว้จริง (ไม่ใช้เหตุผลทั่วไปลอยๆ) จากนั้นถาม user ให้ยืนยัน/ปรับก่อนไปขั้นตอนถัดไปเสมอ — ห้ามเขียนเอกสารจนกว่าจะ confirm stack สุดท้ายแล้ว

## 4. ส่งต่อให้ subagent `tech-stack-writer` เขียนไฟล์จริง

เรียก Agent tool โดยใช้ `subagent_type: "tech-stack-writer"` พร้อม prompt ที่ประกอบด้วย (subagent นี้จะไม่ถาม user เอง ต้องส่งข้อมูลที่ confirm แล้วให้ครบ):

- วันที่ปัจจุบันในรูปแบบ `YYYYMMDD` (ดึงจาก currentDate ใน system context ของบทสนทนานี้ — ห้ามให้ subagent คำนวณเอง)
- scope ของการตัดสินใจที่ confirm แล้วในขั้นตอนที่ 1
- คำตอบทุกหมวดจากขั้นตอนที่ 2 (หรือหมวดที่ข้าม พร้อมเหตุผลที่ข้าม)
- ตารางเปรียบเทียบ stack ทั้งหมดที่เสนอในขั้นตอนที่ 3 พร้อม stack สุดท้ายที่ user confirm แล้ว
- ถ้าเป็นการอัปเดตไฟล์เดิม ให้ระบุด้วยว่าอะไรเปลี่ยนไปจากรอบก่อน

## 5. รายงานสรุปให้ user

หลัง subagent ทำงานเสร็จ สรุปให้ user ทราบ: ไฟล์ที่สร้าง/แก้ (`tech-stack.md`, log), stack ที่เลือกสุดท้ายพร้อมเหตุผลย่อ, และหมวดที่ถูกข้ามไป (ถ้ามี) ไม่ต้อง push ขึ้น GitHub เองโดยอัตโนมัติ — ถามยืนยันกับ user ก่อนเสมอ ตาม convention ที่กำหนดไว้ใน `CLAUDE.md`
