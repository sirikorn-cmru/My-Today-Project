Skill นี้จัดการทั้งกระบวนการสร้าง/ปรับปรุง UI/UX Prototype ของโปรเจกต์ "My Today Project" ตั้งแต่ตรวจสอบ Design System, กำหนดขอบเขต, เสนอแผน, ตัดสินใจเรื่อง version, ไปจนถึงเรียก subagent ให้ลงมือสร้างไฟล์จริง — ขั้นตอนที่ต้องคุยกับ user (ถามคำถาม, เสนอแผน, รอยืนยัน) ทำเองในขั้นตอนนี้โดยตรง ไม่ส่งต่อให้ subagent เพราะ subagent คุยกับ user ไม่ได้

## 0. ตรวจสอบ Design System (`DESIGN.md`) ก่อนเสมอ

เช็คว่ามีไฟล์ `DESIGN.md` ที่ root ของโปรเจกต์หรือไม่ (ห้ามข้ามขั้นตอนนี้แม้ user จะรีบ — Prototype ที่ไม่มี design system อ้างอิงจะไม่สอดคล้องกัน)

- **ถ้ามีอยู่แล้ว:** อ่านเพื่อดึง token สี/typography/spacing และ UI patterns มาใช้อ้างอิงตลอดงานนี้ ไปขั้นตอนที่ 1 ต่อได้เลย
- **ถ้ายังไม่มี:** ต้องหยุดและถาม user ก่อนไปต่อ ให้รวบรวมข้อมูลต่อไปนี้ (ถามทีละเรื่องหรือรวมเป็นชุดคำถามเดียวก็ได้ ใช้ AskUserQuestion):
  1. **โทนสี** ที่ต้องการ — ถ้า user ยังไม่มีไอเดีย ให้เสนอ ≥3 แนวทางพร้อมข้อดี/ข้อเสีย เช่น (ก) โทนอุ่น/earth tone แบบ MUJI — ให้ความรู้สึกสงบ เป็นธรรมชาติ แต่ต้องระวังไม่ให้ดูจืดชืดเกินไป (ข) โทนเย็น/mono เทา-ฟ้า — ดูโปรเฟสชันแนล/เทคโนโลยี แต่จะดูเหมือนแอปทั่วไปมากกว่า (ค) ขาว-ดำ-เทาล้วน + accent เดียว — มินิมอลสุด อ่านง่าย แต่ต้องเลือก accent ให้ดีไม่ให้จืด
  2. **สไตล์/บุคลิก** ที่ต้องการ (เช่น minimalist, warm, corporate, playful) — ถ้า user ไม่ระบุ อ้างอิง positioning ของโปรเจกต์ใน CLAUDE.md ("ไม่ใช่ Task manager", personal daily workspace) เป็นค่าเริ่มต้นที่แนะนำ
  3. **ตัวอย่างภาพโลโก้/reference image** ถ้ามี — ถ้า user แนบภาพมาในแชท ให้ดูภาพเพื่อดึงสี/สไตล์มาอ้างอิงประกอบ
  - หลังได้ข้อมูลครบ **เขียน `DESIGN.md` เองตรงนี้เลย** (ไม่ต้องเรียก subagent เพราะเป็นขั้นตอนที่ต้องคุยกับ user) โดยใช้โครงสร้างเดียวกับที่ CLAUDE.md อ้างถึง: Brand Identity & CI, Design Tokens (Colors/Typography/Spacing), UI Components & Patterns, UX Guidelines & Rules แล้วแจ้ง user ว่าสร้างเสร็จแล้วก่อนไปขั้นตอนที่ 1

## 1. กำหนดขอบเขต (Scope) และแหล่งอ้างอิง

- ถ้า user ระบุขอบเขตมาแล้วอย่างชัดเจน (เช่น "ทำเฉพาะ Sprint 3", "เฉพาะหน้า Dashboard") ใช้ตามนั้นได้เลย
- ถ้า user บอกกว้างๆ ว่า "ทำ Prototype" เฉยๆ โดยไม่ระบุขอบเขต ให้ถามพร้อมเสนอ ≥3 แนวทางพร้อมข้อดี/ข้อเสีย เช่น:
  1. เฉพาะ Sprint/feature ที่เพิ่งพูดถึงล่าสุดในบทสนทนา — เร็ว โฟกัสตรงประเด็น แต่ไม่เห็นภาพรวมทั้ง flow
  2. Sprint ถัดไปที่ยังไม่เริ่ม ตามลำดับใน backlog (เช็คสถานะจริงด้วย `backlog-sync-check` ถ้าจำเป็น) — ตรงกับ roadmap ปัจจุบัน แต่อาจไม่ตรงกับสิ่งที่ user อยากเห็นตอนนี้
  3. ทั้ง roadmap แบบภาพรวม end-to-end (ทุก Sprint ที่มี spec แล้ว) — เห็นภาพรวมทั้งหมดสำหรับ demo/pitch แต่ใช้เวลาทำนานและมีไฟล์เยอะมาก ควรทำเป็นหลายรอบมากกว่าทำทีเดียว
- เมื่อขอบเขตชัดแล้ว รวบรวมแหล่งอ้างอิงที่จะใช้:
  - **Requirement:** ไฟล์ spec ที่เกี่ยวข้องใน `.docs/01-requirements/01-spec/`
  - **Backlog:** entry ที่เกี่ยวข้องใน `.docs/01-requirements/backlog.md`
  - **Feature List:** ถ้ามีเอกสาร Feature List แยกต่างหากอยู่แล้วให้ใช้เอกสารนั้น ถ้าไม่มี (ซึ่งตอนนี้ยังไม่มีในโปรเจกต์นี้) ให้สกัดจาก section "Feature Requirements" ของ spec ที่เกี่ยวข้อง (และ Functional Requirements Master List [[../01-requirements/01-spec/20260806-008-my-today-functional-requirements-master|008]] ถ้าอยู่ในขอบเขต)
  - **User Journey:** ถ้ามีเอกสาร User Journey แยกต่างหากอยู่แล้วให้ใช้เอกสารนั้น ถ้าไม่มี ให้สกัดจาก Business Rules / Acceptance Criteria ของ spec ที่เกี่ยวข้อง (Sprint 6 และ Sprint 11 พูดถึง "Final User Journey" โดยตรง — ใช้เป็นต้นแบบได้ถ้าเกี่ยวข้องกับขอบเขต)
  - บอก user ตรงๆ ในแผน (ขั้นตอนที่ 3) ว่าส่วนไหนเป็นเอกสารจริง ส่วนไหนต้อง derive เอง เพราะยังไม่มีเอกสารต้นทางแยก

## 2. ตัดสินใจเรื่อง Folder + Version

Prototype แต่ละขอบเขตเก็บที่ `.docs/02-design/01-prototypes/{topic-slug}/v{N}/` (`{topic-slug}` เป็น English kebab-case สั้นๆ ที่สื่อถึงขอบเขต เช่น `sprint3-calendar-schedule`, `full-roadmap`)

- Glob หาว่ามีโฟลเดอร์ `.docs/02-design/01-prototypes/{topic-slug}/` อยู่แล้วหรือไม่
  - **ไม่มี:** เป็น v1 ใหม่โดยอัตโนมัติ ไม่ต้องถาม user เรื่อง version (ไม่มีของเดิมให้เลือก)
  - **มีแล้ว (v1, v2, ... อยู่ก่อน):** ต้องถาม user ทุกครั้งว่าจะ:
    - **(ก) สร้าง version ใหม่ (v{N+1})** — เหมาะเมื่อ: มีการเปลี่ยนแปลงเยอะ/กระทบหลายหน้า, ต้องการเก็บเวอร์ชันเดิมไว้เทียบหรืออ้างอิงย้อนหลัง, หรือ version ล่าสุดเคยถูกรีวิว/อนุมัติจาก stakeholder ไปแล้ว (เช็คจาก `.docs/05-log/` ว่ามีบันทึกทำนองนั้นหรือไม่)
    - **(ข) แก้ไข version ล่าสุด (v{N} เดิม) ในที่เดิม** — เหมาะเมื่อ: เป็นการแก้เล็กน้อยตาม feedback ก่อน finalize, หรือ version ล่าสุดยังไม่เคยถูกรีวิวจริงจังเลย
    - ให้คำแนะนำที่ตรงกับสถานการณ์จริงเสมอ (อย่าถามเฉยๆ โดยไม่แนะนำ) พร้อมเหตุผลสั้นๆ ว่าทำไมถึงแนะนำแบบนั้น

## 3. เสนอแผนให้ user รีวิวและยืนยันก่อนเสมอ

**ห้ามเรียก subagent ให้สร้างไฟล์จริงจนกว่าขั้นตอนนี้จะเสร็จ** สรุปแผนให้ user เห็นเป็นข้อความ ประกอบด้วย:

- ขอบเขตที่จะทำ (จากขั้นตอนที่ 1)
- รายชื่อหน้า/screen ที่จะสร้างเป็น prototype และ flow การเชื่อมโยงระหว่างหน้าคร่าวๆ
- แหล่งอ้างอิงที่จะใช้ (spec ไหน, backlog entry ไหน, Feature List/User Journey เป็นเอกสารจริงหรือ derived)
- ตำแหน่ง folder + version ที่จะสร้าง/แก้ (จากขั้นตอนที่ 2) พร้อมเหตุผล
- โทนสี/สไตล์หลักจาก `DESIGN.md` ที่จะใช้ (สรุปสั้นๆ)

รอให้ user ยืนยัน หรือขอแก้แผนก่อน — ถ้า user แก้ไข ให้ปรับแผนแล้วเสนอใหม่จนกว่าจะยืนยัน

## 4. เรียก subagent `prototype-writer` ให้สร้างไฟล์จริง

หลังจาก user ยืนยันแผนแล้วเท่านั้น เรียก Agent tool ด้วย `subagent_type: "prototype-writer"` พร้อมส่ง:

- แผนที่ยืนยันแล้วทั้งหมด (scope + topic-slug, รายชื่อ screen, แหล่งอ้างอิงทั้งหมด, target path พร้อมระบุว่าเป็น new-version หรือ edit-latest)
- วันที่ปัจจุบันแบบ `YYYYMMDD` (ดึงจาก currentDate ใน system context — ห้ามให้ subagent คำนวณเอง)

subagent จะอ่าน `DESIGN.md` เอง แล้วสร้าง/แก้ไข static HTML mockup ต่อหน้าจอ + `tokens.css` + `index.md` ของ version นั้น พร้อมอัปเดต log

## 5. รายงานผลและเสนอเปิดดูใน Browser

- สรุปไฟล์ที่ subagent สร้าง/แก้ไขให้ user ทราบ
- เสนอเปิดดูผ่าน Browser pane (`preview_start` แล้ว `navigate` ไปที่ path ของไฟล์ `.html` ที่สร้าง) เพื่อให้ user รีวิวจริงว่าตรงตามที่คาดหรือไม่
- ไม่ต้อง push ขึ้น GitHub เองโดยอัตโนมัติ — ถามยืนยันกับ user ก่อนเสมอ ตาม convention ที่กำหนดไว้ใน `CLAUDE.md`
