Skill นี้จัดการ workflow ทั้งหมดของการรับ requirement ดิบจาก user แล้วแปลงเป็นเอกสาร spec ที่เป็นทางการของโปรเจกต์ "My Today Project" พร้อมอัปเดต backlog และ log ทำตามลำดับนี้ทุกครั้ง อย่าข้ามขั้นตอน และอย่าเรียก subagent ก่อนที่ข้อมูลจะครบ

## 1. รับ requirement ดิบ

ใช้ requirement ที่ user พิมพ์มา (จาก args ของ skill นี้ ถ้ามี หรือจากข้อความล่าสุดในบทสนทนา) เป็นจุดเริ่มต้น

## 2. สำรวจเอกสารเดิม

ใช้ Glob/Grep สำรวจไฟล์ทั้งหมดใน `.docs/01-requirements/01-spec/` (ไม่รวม `index.md`) และอ่านไฟล์ที่หัวข้อใกล้เคียงกับ requirement ที่ได้รับมา เพื่อดูว่า:

- requirement นี้ซ้ำหรือต่อยอดจากเอกสารเดิมที่มีอยู่หรือไม่
- ถ้า user อ้างอิงถึงเอกสาร requirement เดิมในคำพูด (เช่น "ต่อจาก...", "แก้ไข...", "อ้างจาก...") ให้เปิดไฟล์นั้นมาอ่านเทียบเนื้อหาก่อนตัดสินใจในขั้นตอนที่ 4

## 3. ถามเมื่อไม่แน่ใจ (ต้องมีตัวเลือก ≥3 แนวทางเสมอ)

ถ้าส่วนใดของ requirement ยังไม่ชัดเจนพอจะเขียนเป็น spec ได้ (เช่น scope, user story, business rule, acceptance criteria, กลุ่มผู้ใช้เป้าหมาย) ให้ถาม user กลับด้วย AskUserQuestion **ห้ามถามลอยๆ แบบปลายเปิด** — ทุกคำถามต้องแนบแนวทางให้เลือกอย่างน้อย 3 แนวทางเสมอ (ตัวเลือก "อื่นๆ" มีให้อัตโนมัติอยู่แล้ว ไม่ต้องเพิ่มเอง) เช่น ถ้าไม่รู้ scope ให้เสนอ 3 ระดับ scope ที่เป็นไปได้ให้เลือก แทนที่จะถามลอยๆ ว่า "scope คืออะไร"

ทำซ้ำขั้นตอนนี้จนกว่าจะมั่นใจว่าเนื้อหาเพียงพอจะเขียน spec ได้จริง

## 4. วิเคราะห์ว่าควรสร้างเอกสารใหม่หรือแก้เอกสารเดิม

จากผลขั้นตอนที่ 2:

- ถ้า requirement เป็นเรื่องใหม่ ไม่ทับซ้อนกับเอกสารเดิม → ตัดสินใจสร้างไฟล์ spec ใหม่
- ถ้า requirement เป็นการต่อยอด/แก้ไขเอกสารเดิมโดยตรง → พิจารณาว่าควรอัปเดตเอกสารเดิมแทนการสร้างใหม่
- ถ้ายังตัดสินใจไม่ได้ชัดเจนระหว่าง 2 ทางนี้ ให้ถาม user ด้วย AskUserQuestion พร้อมตัวเลือกอย่างน้อย 3 แนวทาง เช่น "แก้เอกสารเดิม [ชื่อไฟล์]", "สร้างเอกสารใหม่แยกต่างหาก", "สร้างเอกสารใหม่แต่ลิงก์อ้างอิงกลับไปเอกสารเดิม"

## 5. ส่งต่อให้ subagent `requirement-writer` เขียนไฟล์จริง

เมื่อ requirement ชัดเจนครบถ้วนแล้ว (ผ่านขั้นตอนที่ 1-4) เรียก Agent tool โดยใช้ `subagent_type: "requirement-writer"` พร้อม prompt ที่ประกอบด้วยข้อมูลครบทุกอย่างที่ subagent ต้องใช้ (subagent นี้จะไม่ถาม user เอง ดังนั้นต้องส่งข้อมูลที่ clarify แล้วให้ครบ):

- เนื้อหา requirement ที่ clarify แล้วทั้งหมด (เป็นภาษาไทย)
- วันที่ปัจจุบันในรูปแบบ `YYYYMMDD` (ดึงจาก currentDate ใน system context ของบทสนทนานี้ — ห้ามให้ subagent คำนวณเอง)
- คำตัดสินจากขั้นตอนที่ 4 ว่าสร้างใหม่หรือแก้เอกสารเดิม (พร้อม path ไฟล์เดิมถ้าเป็นกรณีแก้ไข)
- slug หัวข้อแบบสั้น เป็นภาษาอังกฤษ kebab-case ไม่มีช่องว่าง/ภาษาไทย (สรุปจาก topic ของ requirement เอง ก่อนส่งเข้า prompt)

## 6. รายงานสรุปให้ user

หลัง subagent ทำงานเสร็จ สรุปให้ user ทราบสั้นๆ ว่า: ไฟล์ spec ที่สร้าง/แก้ (พร้อม path), รายการที่เพิ่มใน `backlog.md`, และบรรทัดที่บันทึกไว้ใน log ของวันนี้ ไม่ต้อง push ขึ้น GitHub เองโดยอัตโนมัติ — ถามยืนยันกับ user ก่อนเสมอ ตาม convention ที่กำหนดไว้ใน `CLAUDE.md`
