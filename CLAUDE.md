### Commands

- `npm install` — install dependencies
- `npm run dev` — start the Vite dev server (default port 5173)
- `npm run build` — type-check (`tsc --noEmit`) then production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run lint` — run ESLint
- `npm run test:rules` — verify `firestore.rules` (Sprint 12's per-user Security Rules) against the Firestore Emulator via `scripts/test-firestore-rules.mjs` — **requires Java 21+** (firebase-tools' emulator no longer supports older JDKs); the emulator/test could not actually be run in the sandbox this was built in (only Java 8 was available there) so this has been reviewed by hand but not executed — run it for real in an environment with Java 21+ before trusting Gate 12's Security Rules acceptance criterion as verified

No app-level test runner is configured yet (no Sprint before 12 required one) — `test:rules` above is Sprint 12's first, narrowly-scoped exception (Firestore Security Rules only, not a general test suite).

Tasks, Events, Life Areas, Profile, Notes, and Links persist to LocalStorage (seeding `src/data/seedTasks.ts` / `src/data/seedEvents.ts` / `src/data/seedLifeAreas.ts` on first run — Profile/Notes/Links have no seed, start empty, since Sprint 8 doesn't need a pre-populated Inbox for the demo to make sense); Files persist to IndexedDB via `src/lib/fileDb.ts` (seeding `src/data/seedFiles.ts` on first run) since file blobs don't fit LocalStorage's string-only, ~5-10MB quota — `useFiles` exposes a `loaded` flag pages must check before rendering, since IndexedDB reads are async unlike the other hooks' synchronous LocalStorage reads; it also exposes both `updateFileLifeArea` (Life-Area-only, used by the delete cascade) and the more general `updateFile` (name/category/lifeAreaId/linkedTaskIds/inInbox patch, used by `FileFormModal`'s edit/organize mode). `useNotifications` derives its list from the live `tasks`/`events` arrays every render (see `notificationUtils.ts`) rather than owning separate stored records — only read/notified state is persisted (`my-today:notifications-read`, `my-today:notifications-notified` in LocalStorage). Only `App.tsx` calls these hooks — don't call them again elsewhere, it would create a second out-of-sync copy of the data
- **Quick Capture / `inInbox` (Sprint 8):** `Task`, `CalendarEvent`, `FileRecord`, `Note`, and `Link` all carry an `inInbox: boolean` field. Quick-Capture-created records get `inInbox: true` and skip that entity's normally-required field (`Task.dueDate`, `CalendarEvent.date`, `Link.url`; `Note`/`FileRecord` have no such field to defer) — every `*FormModal` takes an optional `quickCapture` prop that both relaxes its `canSubmit` check and sets `inInbox` on the submitted input (`inInbox: Boolean(quickCapture)`). "Organizing" an item from `InboxPage` opens that same modal in its normal (non-quickCapture) mode pre-filled from the existing record, which re-enforces the full validation and flips `inInbox` back to `false` on save. `DashboardPage`, `TasksPage`, `FilesPage`, and `calendarUtils.getDayItems` all filter out `inInbox: true` records so an unorganized capture never appears outside `InboxPage` — this is why `notificationUtils.ts`'s `taskLevel`/`eventLevel` also skip `inInbox` (and empty-deadline) records rather than trying to compute a deadline that doesn't exist yet
- **Now/Next/Later Timeline + Smart Priority + Life Progress (Sprint 9):** `src/lib/timelineUtils.ts` is the logic for all three. `smartPriorityTier` ranks a Task/Event into one of 5 fixed tiers — Overdue(0) → Due Today(1) → Upcoming(2) → High Priority(3) → Normal(4) per Business Rule 2 — using only real dates/times/priority compared against "now", deliberately no AI/ML. `getTimelineEntries(tasks, events, lifeAreas, reference)` builds today-only Now/Next/Later buckets (Business Rule 1: Now = overdue or starting within the next hour, Next = later today with a known time, Later = today but no time set) for `TimelinePage`, reusing `smartPriorityTier` to sort within each bucket. `getLifeProgress` computes today-due-only completed/total counts overall and per Life Area (Business Rule 3 — deliberately excludes other days' tasks and never surfaces a "score") for the Dashboard's `LifeProgress` component
- **Task-Event-File-Note-Link linking / "What-When-Information" model (Sprint 10):** `Task` and `CalendarEvent` both carry `linkedNoteIds: string[]` / `linkedLinkIds: string[]` (stored on the Task/Event side) and `reminderLeadTime: number | null` (per-record override of Sprint 5's default notification lead time; `null` = use the system default, see `formatLeadTime`/`reminderLeadTimeOptions` in `taskUtils.ts`). `FileRecord` gained `linkedEventIds: string[]` alongside its existing Sprint 4 `linkedTaskIds: string[]` — both many-to-many relations are stored File-side (a file links out to Tasks/Events, not the reverse), which is why "does this Task/Event have related files" is always computed as `files.filter(f => f.linkedTaskIds/linkedEventIds.includes(id))`. `TaskDetailModal`/`EventDetailModal` (see above) are the UI for all of this — deliberately symmetric implementations (Event's is a near-mirror of Task's minus Priority/Status) per Business Rule 4
- Deleting a Life Area must never delete the Tasks/Events/Files/Notes/Links that reference it (Sprint 7 Acceptance Criteria, extended to Note/Link once those existed in Sprint 8: they "stay, just with no Life Area anymore") — `App.tsx`'s `handleDeleteLifeArea` clears the stale `lifeAreaId` on every referencing record first (via `updateTask`/`updateEvent`/`useFiles().updateFileLifeArea`/`updateNote`/`updateLink`), then calls `deleteLifeArea`. Don't wire `LifeAreasPage`'s delete button directly to the hook's `deleteLifeArea` — it would leave orphaned IDs pointing at nothing
- `useTasks`'s LocalStorage key is `my-today:tasks:v2`, not `my-today:tasks` — Sprint 7 replaced `Task.subject` (free text) with `Task.lifeAreaId`, a breaking shape change, and bumped the key to force a clean reseed instead of writing migration logic (per the spec's own guidance, since there was no real user data yet). If Task's shape changes again the same way (a rename/removal), bump to `:v3` rather than migrating in place. Sprint 8's `inInbox: boolean` addition did **not** need a key bump — it's a pure addition, not a rename, and old stored records simply read back as `inInbox: undefined`, which every `if (record.inInbox)` check already treats as falsy/"not in inbox". Only bump the key for a breaking rename/removal, not for a plain new-field addition that degrades gracefully
- `src/lib/storage.ts` — generic typed LocalStorage read/write JSON helpers (used by Tasks/Events/Notifications/Life Areas/Profile/Notes/Links, not Files)
- `src/lib/lifeAreaUtils.ts` — `getLifeAreaName(lifeAreas, id)`, the one lookup helper every card/list uses to turn a stored `lifeAreaId` into a display name (returns `''` if unset or the Life Area was deleted)
- `src/lib/notificationUtils.ts` — `buildNotifications(tasks, events, readIds)` classifies each non-Done task and each event into `Overdue`/`DueToday`/`DueSoon` (or excludes it) using precise hours-until-deadline math (`dueDate`+`dueTime` combined, not just day-granularity like the Dashboard's existing `isDueToday`/`daysUntil`) — this is intentional: Gate 5 requires distinguishing "24 hours left" from "1 hour left" from "overdue", which day-only comparison can't do. Notification `id`s are keyed by `{kind}-{sourceId}-{level}`, so a task crossing from `DueSoon` into `Overdue` is treated as a new notification (unread again) without any explicit reset logic

### Sprint discipline

Each `.docs/01-requirements/01-spec/*.md` file is one Sprint's contract. Before writing code, read the matching spec's In-scope/Out-of-scope sections and stay inside them — don't implement a later Sprint's features early (e.g. don't wire up real Task persistence while Sprint 1 is still mock-data-only), and don't remove/break a completed Sprint's functionality while building the next one (non-regression rule, stated explicitly in each spec from Sprint 2 onward).

## Project purpose

**My Today — One Life, One Workspace** — a **Personal Daily Workspace** web app (no backend, client-side only), designed around Human-Centered Design so that opening the app immediately answers "what do I need to do today, what matters, what's due soon, what's done?". The target user is **general people managing everyday life** — students, employees, teachers, freelancers, parents, anyone juggling multiple roles — not students exclusively; students remain one supported persona among several, via the **Life Area** concept (see [20260806-007-my-today-sprint7-category-profile.md](.docs/01-requirements/01-spec/20260806-007-my-today-sprint7-category-profile.md); one person has several Life Areas — e.g. Study/Project/Personal, or Work/Finance/Family) rather than student-specific fields/wording. Don't reintroduce student-only terminology (e.g. "Subject"/"รายวิชา" as a required field name) — use "Life Area" instead (not "Category" — renamed on 2026-08-06 to fit the product positioning), with education fields (Student ID, Faculty, Major) kept strictly optional on the Personal Profile.

The pitch is deliberately **not** "a Task manager" (that invites comparison to Todoist/Notion/Google Calendar) — it's: people don't lack apps, their life's information is scattered across too many of them; My Today organizes around a person's life, not around a system an organization built.

| Skill | Produces | Reads from |
|---|---|---|
| `requirement-intake` | New/amended spec doc + `backlog.md` entry + log | Raw requirement text from the user |
| `backlog-sync-check` | Corrected `backlog.md` status | Spec docs + `src/` + git log |
| `feature-journey-sync` | `feature-list.md` + `user-journey-{persona}.md` | `backlog.md` + spec docs |
| `prototype-intake` | Versioned UI/UX mockups under `01-prototypes/{topic-slug}/v{N}/` + `DESIGN.md` (created on first run if missing) | Spec docs + `backlog.md` + `feature-list.md`/`user-journey-{persona}.md` (or the spec directly, for a Sprint those two haven't processed yet) |
| `architecture-doc-sync` | `architecture.md` (Context + Container + Core Domain Concepts) | `backlog.md`/`feature-list.md` + user-journey docs |
| `data-api-doc-sync` | `database-schema.md` + `api-spec.md` | `architecture.md` |

**After a Sprint ships**, run these in this order to keep every derived doc in sync (each is independent enough to stop early if you only need a subset, but later ones assume earlier ones are current): `backlog-sync-check` → `feature-journey-sync` → `architecture-doc-sync` → `data-api-doc-sync` → `detailed-design-doc-sync`. This exact order was used after Sprint 8 shipped (2026-08-23) — it's the order in which each doc's own content feeds the next one. `tech-stack-advisor` isn't part of this chain (it doesn't depend on or feed the others), but once `tech-stack.md` exists, the other three `*-writer` subagents (architecture/data-api/detailed-design) read it to make their own "หมายเหตุการ implement ปัจจุบัน" footnotes precise — so re-run those three after a `tech-stack-advisor` update if the footnotes should reflect a stack change.

### Requirement intake workflow

New requirements should go through the `requirement-intake` skill (`.claude/skills/requirement-intake/SKILL.md`) rather than being hand-written ad hoc. It takes a raw requirement from the user, asks clarifying questions (always with ≥3 suggested approaches to pick from) when anything is ambiguous, decides whether to create a new spec doc or amend an existing one, then delegates the actual file writes to the `requirement-writer` subagent (`.claude/agents/requirement-writer.md`), which creates/amends the spec file, updates `backlog.md`, and appends a summary to today's `.docs/05-log/{YYYYMMDD}-log.md`.

### Backlog sync check

Use the `backlog-sync-check` skill (`.claude/skills/backlog-sync-check/SKILL.md`) to audit whether `backlog.md` is still accurate — both internally (every spec doc has a matching, non-broken backlog entry) and against reality (a Sprint's noted status vs. what's actually been built in `src/` and committed in git). It delegates to the `backlog-auditor` subagent (`.claude/agents/backlog-auditor.md`), which fixes `backlog.md` directly if it's stale but never edits spec files themselves. Run this periodically or whenever backlog accuracy is in question — don't assume a Sprint's "สถานะ" note in `backlog.md` is current just because it was correct when written (e.g. Sprint 1-2 were marked "ยังไม่เริ่ม" well after being implemented, until this check catches it).

### Feature list & user journey generation

Use the `feature-journey-sync` skill (`.claude/skills/feature-journey-sync/SKILL.md`) to generate/update two derived artifacts: `01-requirements/feature-list.md` (see above) and `02-design/01-prototypes/user-journey-{persona}.md` — one Mermaid `flowchart` per persona (currently `student` and `general-person`, matching the dual-persona convention proven in Sprint 6/7's Gate 6/7), with each diagram node mapped back to an FR-ID from the Functional Requirements Master List (`20260806-008-...`) and styled `done` vs `planned` per that step's actual Sprint status in `backlog.md` — never implying a capability exists before it's actually built. The skill proposes MoSCoW ratings and confirms them (plus the persona list) with the user before writing anything, then delegates the actual file writes to the `feature-journey-writer` subagent (`.claude/agents/feature-journey-writer.md`). It reads `backlog.md` as-is rather than auto-chaining into `backlog-sync-check` first (to avoid stacking two audits every run) — if backlog accuracy is in doubt, run `backlog-sync-check` beforehand instead of trusting this skill's own lightweight staleness check.

### Prototype generation

Use the `prototype-intake` skill (`.claude/skills/prototype-intake/SKILL.md`, added 2026-08-29) to create/update UI/UX prototypes — self-contained, static HTML/CSS mockup screens (no CDN/external dependency, so they open and render correctly fully offline) under `02-design/01-prototypes/{topic-slug}/v{N}/`, drawing on the relevant spec doc(s), `backlog.md`, and `feature-list.md`/`user-journey-{persona}.md` (falling back to deriving the equivalent content directly from a spec's own Feature Requirements/Business Rules/Acceptance Criteria sections if that Sprint hasn't been processed by `feature-journey-sync` yet — e.g. a spec fresh out of `requirement-intake`). It always checks for `DESIGN.md` at the repo root first — a design-system doc (Brand Identity & CI, Design Tokens, UI Components & Patterns, UX Guidelines) that **does not exist yet** in this repo — and if missing, stops to ask the user for color tone/style/reference images (≥3 suggested directions with pros/cons) and writes `DESIGN.md` itself before touching any prototype. It always proposes a plan (scope, screens, sources, target folder+version, design tokens to be used) for the user to review/confirm before creating anything, and on a repeat run for a `{topic-slug}` that already has a version folder, always asks whether to start a new version (`v{N+1}`) or edit the latest one in place — with a situational recommendation either way, never a bare question. Only after confirmation does it delegate the actual file writes to the `prototype-writer` subagent (`.claude/agents/prototype-writer.md`), which also writes that version's `index.md` and a log entry.

Like `feature-journey-sync`, it reads `backlog.md`/`feature-list.md` as-is rather than auto-chaining `backlog-sync-check`.

## Working conventions

- `.claude/settings.local.json` is gitignored (local machine config) — do not commit it.
- Keep this file itself committed and up to date — if you change it, commit it in the same batch as the doc changes it describes.
- `DESIGN.md` (repo root, alongside this file) is the product's design system, referenced by `prototype-intake`/`prototype-writer` — it does not exist yet as of 2026-08-29; the first `prototype-intake` run creates it from the user's answers (color tone, style, reference images), not from any hardcoded default.
- If a `*-doc-sync` skill finds that a spec doc contradicts the real code/architecture (e.g. Sprint 10's spec claiming `Task.linkedFileIds` already existed, caught by `data-api-doc-sync` on 2026-08-23 — see that Sprint's spec doc and `database-schema.md`/`api-spec.md`'s Known Gaps sections), don't silently fix the spec yourself — flag it prominently to the user and, if they want it corrected, run `requirement-intake` to amend the spec doc afterward, rather than editing it inline from within the doc-sync skill.
- A stray `.obsidian/` folder can appear at the repo root (distinct from the tracked `.docs/.obsidian/`) if the whole repo is ever opened directly as an Obsidian vault — it's gitignored (see `.gitignore`) and unrelated to the vault's own config; don't confuse the two or try to track the root-level one.
- A "no new feature" Sprint (Sprint 6, Sprint 11) can still gain a new feature via an explicit, cited exception to its own Business Rule — don't treat "no new feature" as absolute. Precedent: Sprint 6 added the whole Privacy Notice/Terms of Use page (real new UI) despite its own "ห้ามเพิ่ม Feature ใหม่" rule, because it was mandated by a newly-formalized compliance requirement, not scope creep; the same pattern was reused on 2026-08-23 to add Sprint 11's IndexedDB Quota-Warning mechanism, explicitly citing the Sprint 6 precedent in the amendment. When proposing this pattern again, always cite the specific prior amendment as precedent rather than asserting the exception is fine on its own.
